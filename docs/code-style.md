# Code Style

These are hard rules for this project, not loose preferences — apply them consistently across `apps/`, `services/`, and `packages/`. Biome enforces formatting (quotes, semicolons, trailing commas, line width) automatically; this doc covers the choices a formatter can't make for you.

## These rules outrank library/framework/tool defaults

Docs, MCP tools (`context7`, the Chakra MCP, …), and skills (`chakra-ui-builder`, `vercel-react-best-practices`, …) all return example code in *that library's own house style* — arrow-function components, `interface`, inline object/array props, sometimes default exports. That's normal for general-purpose reference material; it is not this project's style.

When writing or hand-editing code in this repo, treat any such example as showing *what the code should do* (which props exist, how an API works), never *how the syntax should be shaped*. Keep the logic, rewrite the shape to match this doc — arrow → `function`, `interface` → `type`, inline literal → named declaration, default export → named export, params destructured in the body not the signature.

The only two exceptions today are documented below, and both exist because the code genuinely fails otherwise — not because a library "usually" does it that way:

- Next.js's required default exports on specific route files and `next.config.ts` — see [Exports](#exports).
- `apps/website/src/components/ui/**`, the Chakra CLI-generated snippet directory — regenerated by tooling and out of scope entirely, not an in-place exception — see [Generated/vendored code](#generatedvendored-code).
- `next/font/google` (and `next/font/local`) loader calls, e.g. `Geist({ subsets: ["latin"] })` in `apps/website/src/app/layout.tsx` — Next.js's build-time SWC transform statically parses this exact call expression and rejects anything it can't parse that way (it explicitly errors on a spread in the arguments). Passing a variable instead of the object literal breaks that static analysis, so the options object must stay inline at the call site — this is the one place [Declare before use](#declare-before-use--no-inline-functions-objects-or-arrays) doesn't apply.

A new exception is only valid if it's added here the same way: scoped to an exact file or directory, with the concrete technical reason the code won't work otherwise. "The library's docs/examples look like this" is never sufficient justification on its own.

## Functions

- **Always `function`, never arrow functions — no exceptions.** This includes top-level functions, React components, hooks, and inline callbacks: `array.map(function (x) { ... })`, `useEffect(function () { ... }, [])`, `onClick={function () { ... }}`. A one-liner callback is not an exception.
- Class/object methods use method shorthand (`class Foo { bar() {} }`, `const obj = { bar() {} }`) — that's already function-style, not an arrow, so no conflict with the rule above.
- **Exception**: arrow function class fields (`class Foo { bar = () => {} }`) are allowed specifically when `this` must be auto-bound — e.g. a method passed directly as a callback/event handler. Keep this exception narrow and deliberate.
- Async code always uses `async function` + `await`. Don't write raw `.then()` chains.

## Declare before use — no inline functions, objects, or arrays

Don't define a function, object, or array literal inline at the point it's used — as a JSX prop, a callback argument, or any other call-site position. Declare it first (module scope if it's static, inside the function body via `useMemo`/`useCallback` if it depends on props/state/closure) and pass it by name.

```tsx
const navLinkHoverStyle = { color: "fg" };

function renderNavItem(item: NavItem) {
	return (
		<ChakraLink key={item.href} asChild color="fg.muted" _hover={navLinkHoverStyle}>
			<NextLink href={item.href}>{item.label}</NextLink>
		</ChakraLink>
	);
}

function NavList(props: NavListProps) {
	const { items } = props;
	return <HStack as="nav">{items.map(renderNavItem)}</HStack>;
}
```

not:

```tsx
function NavList(props: NavListProps) {
	const { items } = props;
	return (
		<HStack as="nav">
			{items.map((item) => (
				<ChakraLink key={item.href} asChild color="fg.muted" _hover={{ color: "fg" }}>
					<NextLink href={item.href}>{item.label}</NextLink>
				</ChakraLink>
			))}
		</HStack>
	);
}
```

This is separate from, and in addition to, the no-arrow-functions rule above — `items.map(function (item) { ... })` still violates this rule even though it satisfies that one, because it's still defined inline. Extract it to a named function declared before the call.

Two reasons this matters, both hard rules, not style preference:

- **Readability.** A named declaration reads top-to-bottom: the reader sees the label (`renderNavItem`, `navLinkHoverStyle`) before they need to understand its contents, instead of parsing an anonymous blob at the call site.
- **Referential stability.** An object, array, or function literal written inline is a *new reference on every render*. Passed as a prop, it makes the receiving component see a "changed" prop even when the contents are identical — this defeats `React.memo`, and breaks `useEffect`/`useMemo`/`useCallback` dependency arrays that include it, causing extra re-renders or effect re-runs that are hard to trace back to the cause.

Rule of thumb: a function-call argument or JSX attribute value must be either a bare reference to something already declared (a variable, a prop, a property-access chain) or a literal primitive written directly as itself (`"ok"`, `404`, `true`) — never a *constructed* value assembled at that position. Object literals, array literals, function literals, and template literals with interpolation are all constructed values; name them first.

**This applies at every nesting depth, not just the outermost call.** An object literal passed to `z.object({...})` is itself a declaration and is fine to write inline — but if one of *its* properties is itself built by calling another function, that inner call's argument follows the same rule, regardless of how deep it sits:

```ts
const directions = ["north", "south", "east", "west"] as const;

const playerMoveMessageShape = {
	type: z.literal("player-move"),
	direction: z.enum(directions),
};
```

not:

```ts
const playerMoveMessageShape = {
	type: z.literal("player-move"),
	direction: z.enum(["north", "south", "east", "west"]),
};
```

Being nested inside another object/array literal that's itself being assigned to a name does **not** exempt it — `z.enum([...])` is its own call with its own inline array argument, so it needs its own declared name. The only thing that legitimately ends the chain is a plain `const identifier = <literal>;` statement: that *is* the declaration the rule asks for, so its own contents don't need further splitting out.

**Template literals with interpolation count as constructed values too**, the same as objects/arrays/functions — `` `client listening on ${server.url}` `` is built from a variable, not written as itself, so it needs a name before it's passed to `logger.info(...)` or used as a JSX attribute:

```ts
const startupMessage = `client listening on ${server.url}`;
logger.info(startupMessage);
```

A template literal with no interpolation (`` `plain text` ``) is just a string written a different way and doesn't need this — only interpolation makes it a constructed value. Plain arithmetic that reduces to a primitive (`x / 2 - y / 2`) is not covered by this rule; it's still a primitive value, not an object/array/function/interpolated-string.

This applies everywhere, not just JSX: callback arguments (`.map`, `.filter`, `.sort`, event handlers), config objects passed to a function, default parameter objects, all of it.

## JSX expression containers: no inline computation

A JSX expression container — the `{...}` you write between tags to insert a value — must hold only a reference to something already computed: a variable, a prop, a property-access chain (`item.label`), or a simple template literal. Never write a transformation, a conditional, or a destructure directly inside `{}`. Compute it into a named constant before the `return` statement (or at module scope, if it doesn't depend on props/state) and reference that constant in the JSX.

This covers, at minimum:

- Array transforms: `.map()`, `.filter()`, `.reduce()`, `.sort()`, `.find()`, `.flatMap()`
- Conditional rendering: `condition ? <A /> : <B />`, `condition && <A />`
- Destructuring written inline inside the expression

```tsx
function NavList(props: NavListProps) {
	const { items } = props;
	const renderedNavItems = items.map(renderNavItem);

	return <HStack as="nav">{renderedNavItems}</HStack>;
}
```

not:

```tsx
function NavList(props: NavListProps) {
	const { items } = props;

	return <HStack as="nav">{items.map(renderNavItem)}</HStack>;
}
```

And for conditional rendering:

```tsx
function CharacterPanel(props: CharacterPanelProps) {
	const { player } = props;
	const panelContent =
		player === undefined ? (
			<CharacterForm />
		) : (
			<CharacterStats player={player} />
		);

	return <aside>{panelContent}</aside>;
}
```

not:

```tsx
function CharacterPanel(props: CharacterPanelProps) {
	const { player } = props;

	return (
		<aside>
			{player === undefined ? (
				<CharacterForm />
			) : (
				<CharacterStats player={player} />
			)}
		</aside>
	);
}
```

Why: a reader scanning JSX is parsing markup structure. Every `{...}` that contains logic forces them to stop and mentally execute code mid-layout. A named constant separates *what gets computed* from *where it goes* — the JSX becomes a flat list of placeholders, and each computation gets a name that states its purpose before you ever see it used. This is the JSX-specific case of [Declare before use](#declare-before-use--no-inline-functions-objects-or-arrays); it's called out explicitly here because JSX's `{}` syntax makes it easy to reach for inline logic out of habit.

## Parameters & destructuring

Destructure inside the function body, not in the signature:

```ts
function updatePlayer(props: UpdatePlayerProps) {
  const { id, name } = props;
  // ...
}
```

not:

```ts
function updatePlayer({ id, name }: UpdatePlayerProps) {
  // ...
}
```

## Exports

Named exports only — no default exports, including for React components.

```ts
export function PlayerCard(props: PlayerCardProps) { ... }
```

not `export default function PlayerCard(...) { ... }`.

**Exception**: in `apps/website`, Next.js's own file conventions require a default export — route files (`page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, `not-found.tsx`, `template.tsx`, `default.tsx`) and `next.config.ts`. This is framework-mandated, not a style choice; keep it scoped to exactly those files (enforced via the `overrides` in `apps/website/biome.json`) and use named exports everywhere else, including in `apps/website`'s own components, `src/lib/`, and `src/app/actions/`.

## React components

Function declarations, matching the no-arrow-functions rule:

```tsx
function PlayerCard(props: PlayerCardProps) {
  const { name, level } = props;
  return <div>...</div>;
}
```

not `const PlayerCard = (props: PlayerCardProps) => { ... }`.

## Types

- Use `type` for everything — object shapes, unions, function signatures. Don't use `interface`.
- Enums: union string literal types, never TS `enum`.
  ```ts
  type Direction = "north" | "south" | "east" | "west";
  ```
  Plain string values serialize cleanly over WebSocket/JSON and read clearly in logs; numeric `enum` values don't.
- `null` vs `undefined`: `undefined` is the only "no value" your own code should produce — optional fields (`field?: string`), missing values, etc. Don't explicitly assign or check for `null` in code you control. `null` may still show up from external library/DB types (e.g. some Supabase query results) — handle that at the boundary where it enters, then normalize to `undefined`.

## Errors

- Throw typed errors, not plain `Error` or strings. Define a subclass per failure kind:
  ```ts
  class InvalidTargetError extends Error {}
  class InsufficientManaError extends Error {}
  ```
  so `catch` blocks can branch on `instanceof` instead of parsing messages.
- Catch at boundaries — route handlers, WS message handlers, top-level service entry points. Don't wrap every internal call in its own try/catch.

## Naming

- Files: kebab-case everywhere, including React component files — `combat-engine.ts`, `player-card.tsx`. The filename doesn't need to match the exported identifier's casing.
- Exported functions/variables: camelCase. Types: PascalCase. React components (the exported identifier, not the filename): PascalCase.

## Logging

Use the structured logger (pino) in `services/` and any server-side code in `apps/`. Don't use `console.log`/`console.error` outside of quick local debugging that gets removed before committing.

## Comments

No comments unless they explain a non-obvious *why* — a hidden constraint, a workaround, a subtle invariant. Never explain *what* the code does; well-named functions and variables already do that.

## Generated/vendored code

`apps/website/src/components/ui/**` (the Chakra UI provider, color-mode, toaster, tooltip, … snippets) is generated by `npx @chakra-ui/cli snippet add`, not hand-written. Don't hand-edit it to match the rules above — regenerate it via the CLI instead, and treat its arrow functions, `const`-assigned components, `forwardRef` usage, `interface` types, inline object/array literals, etc. as out of scope for this doc.

This exemption is scoped exactly to that directory. It does not license copying those patterns (arrow functions, inline literals, `interface`, …) into any other file just because they were seen there or in a library's own docs/examples — including other files in `apps/website` that sit next to this directory. When writing or reviewing non-vendored code, check the file's own path against this list, not the patterns visible in nearby vendored files.
